# WSM Crypto Algorithm Analysis

Reverse-engineered internals of Samsung's WSM (Wearable Security Module) authentication as implemented in the ARM32 `libwsm.so`. The wire protocol is specified in [PROTOCOL.md](PROTOCOL.md). This document describes the algorithm and the binary's internals.

## Overview

WSM authentication is a three-message ECDH handshake:

1. Camera → phone: challenge (70 bytes)

2. Phone → camera: response (102 bytes)

3. Camera → phone: confirmation (35 bytes)

The crypto stack is **ECDH (P-256) + SHA-256 + HMAC-SHA256**. A **white-box AES** table inside the library is used only to expand the 2-byte nonces to 16 bytes. The initial handshake requires no other white-box operations.

## Packet Formats

### Challenge (70 bytes, camera → phone)

```
Offset  Size  Field
0       1     Version (0x00)
1       1     Type (0x00 = challenge)
2       1     Length (0x46 = 70)
3       65    EC public key (P-256 uncompressed: 04 || X[32] || Y[32])
68      2     Nonce
```

### Response (102 bytes, phone → camera)

```
Offset  Size  Field
0       1     Version (0x00)
1       1     Type (0x01 = response)
2       1     Length (0x66 = 102)
3       65    EC public key (P-256 uncompressed)
68      2     Nonce
70      32    HMAC-SHA256 (client HMAC)
```

### Confirmation (35 bytes, camera → phone)

```
Offset  Size  Field
0       1     Version (0x00)
1       1     Type (0x02 = confirm)
2       1     Length (0x23 = 35)
3       32    HMAC-SHA256 (server HMAC)
```

## Context Structure (176 bytes, 0xB0)

`WSM_Client_init` / `WSM_Server_init` allocate a 176-byte context:

```
+0x00  4B   Handle ID (returned to caller)
+0x04  4B   Type (1 = client)
+0x08  4B   State (1=INIT, 2=CHALLENGE_DONE, 4=HAS_ESAP_KEY)
+0x0C  4B   EC key group pointer
+0x10  4B   EC public key buffer pointer
+0x14  4B   EC public key size (0x41 = 65)
+0x18  4B   Server ID string pointer (MAC address)
+0x1C  4B   Client ID string pointer (MAC address)
+0x20  32B  ECDH shared secret
+0x40  48B  ESAP key (re-auth only)
+0x70  2B   Challenge nonce (from the camera)
+0x80  2B   Response nonce (generated by the client)
+0x90  16B  Expanded challenge nonce
+0xA0  16B  Expanded response nonce
```

## Client Handshake (WSM_Client_checkAndGenerateServerChallenge)

The client turns the 70-byte challenge into the 102-byte response:

1. `find_ctx_by_id(handle)` resolves the context pointer.

2. Validates the challenge header (version 0, type 0, length 70).

3. Validates the context (type 1 = client, state 1 = initialized, key size 65).

4. Stores the challenge nonce: `ctx[0x70..0x71] = challenge[68..69]`.

5. `internal_74e0(ctx+0x70, ctx+0x90)` expands the challenge nonce to 16 bytes.

6. `crypto_gen_random(2, ctx+0x80)` generates the 2-byte response nonce.

7. `crypto_gen_ecc_secret(ctx, challenge+3, 65)` computes the ECDH shared secret into `ctx+0x20`.

8. Builds the response header (version 0, type 1, length 0x66).

9. Copies the client EC public key to `response[3..67]`.

10. Copies the response nonce to `response[68..69]`.

11. `get_client_hmac(ctx, response+70)` writes the 32-byte HMAC to `response[70..101]`.
 
12. Sets state to 2 (CHALLENGE_DONE).

## Client HMAC (get_client_hmac, VA 0x7CA8)

```
key         = SHA-256( shared_secret[32] || expand_nonce(challenge_nonce)[16] || server_id || client_id )
client_hmac = HMAC-SHA256( key, challenge_nonce[2] || response_nonce[2] || server_id || client_id )
```

`server_id` and `client_id` are the two Bluetooth MAC address strings (17 ASCII bytes each, e.g. `C8:38:70:3F:97:75`), used as raw bytes without a null terminator.

## Server HMAC (confirmation)

The 35-byte confirmation carries the camera's HMAC over the same secret, with the nonce order and the ID order both reversed relative to the client HMAC, and with the key derived from the expanded *response* nonce:

```
key         = SHA-256( shared_secret[32] || expand_nonce(response_nonce)[16] || server_id || client_id )
server_hmac = HMAC-SHA256( key, response_nonce[2] || challenge_nonce[2] || client_id || server_id )
```

`WSM_Client_checkClientResponse` recomputes this and compares it against `confirmation[3..35]`; a match completes mutual authentication.

## Nonce Expansion (internal_74e0, VA 0x74E0)

Nonce expansion maps a 2-byte nonce to 16 bytes through a fixed 256-entry x 8-byte lookup:

```
expand_nonce(nonce) = table[nonce[0]] || table[nonce[1]]
```

Each 8-byte half is produced by a white-box AES CBC decrypt over an embedded lookup table (`.data`, file offset 0x32004): 129 blocks of 16 bytes where `block[0]` is the IV and `block[1..128]` are ciphertext. Nonce byte `b` selects entry `b >> 1` and half `b & 1`. The mapping is fixed, so it is captured once as the 2048-byte table embedded in the reimplementation (the README covers the dump procedure).

## ESAP Key (get_esap_key)

After a successful handshake the library can derive a 48-byte ESAP key for re-authentication and app-level encryption:

```
random  = crypto_gen_random(16)
derived = crypto_pbkdf(shared_secret, random, ...)
esap    = crypto_wb_encrypt(derived)   // 48 bytes
```

This path is not used by the live-view flow.

## White-Box AES

The `.data` section embeds the WB-AES lookup tables (~570 KB total): DecT0 (160 KB), DecT1 (320 KB), DecT2 (72 KB), DecTin (8 KB), DecTout (8 KB). They implement AES with the key baked into the tables. They back nonce expansion (captured as the fixed table above), ESAP key derivation, the re-auth HMACs (`get_reauth_*`), and `WSM_encrypt` / `WSM_decrypt`. The initial handshake needs none of them beyond the pre-captured nonce table.
